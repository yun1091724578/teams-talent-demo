一、核心问题：最终解决什么，短期先做哪一类

一句话

Coding agent 在用户自己的仓上会反复犯同一类错误：用户纠正过，下次还犯；换一个基座模型，原来好用的地方悄悄掉点。今天修这些靠人——看抱怨、猜原因、改提示词、上线再看。本项目让这件事在 iCode 服务端自动发生：从用户已有的会话里把错误变成可复跑的题，自动找原因、提改动、配对验证，最后把一份可检查的「进化提案」交给用户确认。

最终要解决的问题：让 agent 在真实使用里自己变好

落到 iCode 上是四个场景。它们走同一套流程，只在数据来源与评测侧重上不同（展开见第七节）：

场景用户遇到的情况（举例）我们给出什么
A 越用越好用户提醒过 agent「Gemini 那边的钩子是不是也要改」，下次改同类代码，它又只改了眼前这一处把纠正过的这类错误变成可复跑的题，找到并验证让它不再复发的改动
B 模型适配换了新基座，原来稳定的某类任务悄悄掉点，没人说得清掉在哪固定回归集上新旧模型配对重跑，给出逐类掉点清单与针对性的 harness 修正
C skill 管理团队为旧版本写的一批 skill，换版本后有的已经多余、有的反而干扰每个 skill 一个「保留 / 失效 / 需调整」判定，附有无对照的证据
D 能力迁移某个团队沉淀出好用的 skill 与工程规范，别的团队想用，但不知道哪些是通用的抽出带适用边界的知识条目，在目标团队的题上验证不掉点

短期先做的一类：变更传播完备性——「改一处，漏一条路」

短期从场景 A 里取一类问题，把闭环完整走一遍、展示效果。这一类是：共享状态（或契约）有多条读写路径，agent 的变更只传播到其中一部分，路径之间随之失配。错误不在 agent 写下的代码里，而在它没写的地方，属于遗漏型缺陷（error of omission）。所以 agent 自查很难发现，只测改动点的验证器也很难发现。一位用户在会话开头就把这个机制说得很准：

"This creates an inconsistency where stale sessions are cleaned up in some code paths but not others."
（译：这造成了不一致：过期会话在一些代码路径里被清理了，在另一些路径里没有。）
——cli-task-19def0-stale-session，会话 ev0（逐字）

这是软件工程的老问题，叫变更传播（change propagation），代码结构上的表现叫散弹式修改（shotgun surgery）。Park 等人在 Eclipse 与 Mozilla 上实测发现，22%–33% 的 bug 修完还要再补修，而且漏改比写错更难被发现（An Empirical Study of Supplementary Bug Fixes，《补充性缺陷修复的实证研究》，MSR 2012，DOI 10.1109/MSR.2012.6224298）。放到 coding agent 上，问题换了一种形态：人类开发者靠经验和评审补全传播面，agent 只能看到上下文里的那一部分。

为什么先做这一类：在真实会话造出的题里，这类要求很常见，模型在上面明显更容易失败；而且错误出在 agent 没写的地方，自查和只测改动点的验证都难发现，正需要演进来补。按「另外那条路径是从哪来的」，这类问题分五种（失败率只算明确做对或做错的运行）：

种类含义例模型失败率
多种实现同一流程有多种实现：多 agent、多平台、多配置Claude 与 Gemini / OpenCode；桌面与无显示器 Linux26 次挂 10 次（38%）
多个阶段同一状态在多个生命周期阶段被读写，或同一动作重入TurnStart 与 TurnEnd；enable 与 disable；hook 重跑30 次挂 8 次（27%）
多个入口同一状态有多个入口、调用方或读取视图直接 Load 与包装函数；暂存区视图与工作区视图46 次挂 11 次（24%）
已有另一份实现同一逻辑已有另一份实现，应当复用或保持一致已有 paths.RepoRoot() 缓存却另写一套（408b8c）16 次挂 1 次（6%）
多方同时读写多个并发参与者读写同一资源两个配置项共用一把锁；另一进程尚未写完的文件4 次挂 0 次

三条路径怎么分工：何时查、查到哪、凭什么知道

三条演进路径（定义见第十二节）在这一类问题上各管一段：A 管「何时查」，变更触及共享状态时触发检查；B 管「查到哪」，用代码定位与代码分析从改动点找出传播面上的每条路径，并逐条确认改到位；C 管「凭什么知道」，提供代码图谱、开发范式与文档里的依赖和约定，补上代码分析看不到的那部分。只做其中一条，都会以可预期的方式失败：

可行性：这一类问题的传播面大多是代码里显式存在的结构，B 的代码定位与分析能查出来。Gemini rewind 的七处写回各自拼路径，都是同一类写回调用；Stale-session 的七个入口都读同一份状态文件；Empty-repo 漏掉的 Gemini 钩子里，调用和错误信息与 Claude 钩子逐字相同。查不到的那部分恰好是 C 要补的：Attribution 一案，调用图查不到「归因读的内容要与 checkpoint 同源」这条依赖，要沿数据来源走两跳；而公开的代码图谱工作只有文件、类、函数节点和调用、继承边，没有「状态」节点与读写边。

在六个案例各自的基准提交上，我们离线查过 C 的四类知识能否提前推出漏掉的路径：

知识来源能 / 部分 / 不能说明
代码图谱式查询5 / 1 / 0最有效，与 B 的代码定位最接近；Attribution 一案要沿数据来源走两跳才查得到
历史共变2 / 3 / 1次之。需要细到函数级（同文件漏改时文件级无效），过滤高频枢纽文件，并区分好坏范式
轨迹经验0 / 4 / 2同题之外的复用信号还弱，要靠跨会话累积；用户纠正天然是「漏了哪条路」的监督信号
仓库文档0 / 2 / 4最弱。这批题的文档几乎不写不变量，Prompt-source 的文档写的还是这次要去掉的旧行为

这是可行性检查，不是闭环实验：「代码图谱能查到」是用代码检索在基准提交上模拟的查询，共变只用基准之前的历史。

已走通的闭环：408b8c，v1→v7（这一类的边界题）

408b8c 是把「归因 → 提改动 → 配对重跑 → 判定」完整走通的一道题：用户要让 GetWorktreePath 像 RepoRoot 一样可缓存，iCode 三次都另建了一套缓存，用户纠正说 "paths.RepoRoot() already implements the same cwd-keyed caching"（paths.RepoRoot() 已经实现了同样的按当前目录缓存）。它属于上表的「已有另一份实现」，是这一类的边界题：agent 读过已有实现仍另写一份，缺的是判断而不是信息，正好说明路径 A 的 skill 能修这种决策缺口。失败的版本也照列：

版本 改了什么 结果 这一步说明了什么
v0 基线—0.833×3，J1 0/3，+42/-1起点：三次都自建缓存
v1新增 skill，但文件放错位置0.833，J1 0/1改动没被加载——「改了没生效」
v2修好结构，只改正文0.833，J1 0/1正文仍没被加载
v3改 description 触发词1.0 / 1.0 / 0.333，J1 3/3，+4/-4能触发了，但不稳定
v4换成无关示例，排除泄题触发 2/2，未判分确认不是靠泄题
v5扩大触发面范围失守，未跑这道题泛化过头
v6写明适用范围1.0×3，J1 9/9，+3/-7有效，但触发贴着题面措辞
v7改为 DRY 原则式判据（duplication-check）1.0×3，J1 9/9，+3/-7有效，且触发不再依赖题面句式

J1 写法：「x/3」指运行次数，「x/9」指判词票数（3 次 × 3 个判官）。

只用一条路径看，v1–v2 会被误判成「能力不行」（其实改动没被加载），v5 会被误判成「这个方向有效」（其实触发范围失守）。回归的 3 道题、5 次有效运行里，没有检查点因 v7 由过变挂。证据只有 1 道主题题、单个模型，远不足以说明这一类问题已经解决。

短期路线

  1. 题集：主题题是 Gemini rewind、Prompt-source、OpenCode-native、Session-agent、Attribution 五道，都属于这一类，而且模型会挂；Stale-session、Empty-repo 作对照。先去掉题面提示，做一版只给原始需求、不点名路径的题面，这样才能真正度量「补全传播面」的能力。
  2. 验证器：每道题都故意改坏其中一条路径，确认验证器能发现——验证器自己也会漏路径。
  3. 知识（离线，可以先做）：在 entireio/cli 上建状态读写图与函数级共变表，用六个案例做历史回放，看推出的传播面是否包含漏掉的路径。
  4. 闭环：A 加触发，B 接代码定位、变更影响分析与跨路径测试生成，C 接上述知识，在去掉提示的题面上比较 v0 与各种组合，留出题按子类分层。
  5. 外推：找 entireio/cli 以外的多变体产品会话（多平台、多协议版本、多租户配置）补题，检验「多种实现」这种问题是不是只是这个仓的特点。

二、交付什么：优化后的 agent 版本，连同能检查的证据

本项目是 iCode 里的 iCode-Talents 模块。对外交付两样：给接入仓的用户 / 团队一个优化后的 agent 版本，附可逐条检查的证据；给 iCode-Core（agent 主线）带成绩单的 Agent 侧候选改动。两样都由我们建设的 Talents 平台产出。

Talents 平台是我们（iCode-Talents）自己建设、运维的系统，不是交付给别人的东西：七个组件（接入服务、轨迹库、造题流水线、评测集群、演进引擎、版本与产物库、进化提案门户）跟着 iCode 服务端部署，在后台持续产出上面两类交付（第三节）。

用户不需要相信我们的结论，每一条改动都能回到证据上去看。穿刺实验已经按这个方式留证：逐题展开，被拒的版本也照列（第九节）。

三、怎么部署：跟着 iCode 服务端，用户无感

Talents 平台跟着 iCode 服务端部署（云端或域内），在 iCode 已经收到的轨迹上，于服务器侧自动触发演进，用户无感。用户只在两处参与：接入时提供能跑通主分支、测试全绿的运行环境；演进有结果后，在门户里检查并确认一份「进化提案」。

为什么跟着 iCode 服务端部署

轨迹本来就在服务端

iCode 的会话、工具调用、模型请求都经过服务端与模型网关。Talents 部署在旁边，不需要用户导出、上传任何东西——这是「用户无感」的前提，也是数据不出域的前提。

演进在服务端做

造题、跑评测、试改动都是批量的容器任务，放在服务端的评测集群里，按租户预算、在空闲时段跑，不占用户的机器与时间。

改动在服务端生效

用户确认的 skill、工具、提示词、知识条目作为「仓级 / 团队级配置」由服务端下发给 iCode 客户端，客户端不用升级。

部署分云端（随 iCode 云服务，按租户隔离）与域内（随 iCode 私有化部署，数据不出域）两种包；演进由新会话积累、新基座上线、skill 库变化或用户手动发起触发，全部在后台排队，用户唯一会感知到的是一份新的「进化提案」。

部署架构

Talents 的七个组件与第八节的七个工作域一一对应（图中每个组件右上角标出对应的工作域）。它们和 iCode 服务端放在同一机房 / 同一域内，产出只有两条出口：用户确认过的用户侧配置回到 iCode 服务端按仓下发；Agent 侧候选连同成绩单交给 iCode-Core 的发布流水线。

用户怎么接入：提供环境，平台验收「绿基线」

① 登记仓库

仓库地址、主分支、只读授权。

② 提供运行环境

Docker 镜像（或 Dockerfile / devcontainer 配置），并声明构建命令与测试命令。

③ 平台验收绿基线

在主分支最新提交上，用用户的镜像构建成功、全部测试通过；连跑 3 次结果一致。不一致的测试列成清单交用户确认（修掉，或显式标为「不稳定、不参与判分」）。产出一份接入报告：构建耗时、测试数、不稳定测试清单。

④ 授权轨迹的使用范围

只用于本仓 / 本团队；是否允许脱敏后参与 Agent 侧的共性改进（默认否）。

完成后该仓状态变为「已接入」，平台开始从它的历史会话自动造题。

从接入到生效

用户侧改动（skill、知识条目、仓级提示词）由 iCode 服务端按仓下发，或以合并请求进用户仓库，可一键回滚；Agent 侧改动随 iCode 正式版本发布，由 iCode-Talents 与 iCode-Core 共同审核，不让单个用户确认。

四、核心竞争力：不只是造题

竞争力来自整个项目几块积累的叠加：先是别人拿不到的原料，再是用好原料的方法与积累。下面按「别人难追上的程度」排：

  1. 我们的位置：私有产品仓、可执行环境、真实会话三样都在手里。做 RSI 要把真实用户的任务变成能反复跑、能自动判分的题，三样缺一不可，我们三样都有：

    • 私有产品仓：iCode 的会话就发生在公司自己的产品仓上。这些仓有完整的提交历史，能回到会话起点重建现场，题出自真实产品，而不是开源仓或合成任务。
    • 可执行环境：用户接入时提供运行环境，平台验收「绿基线」（第三节），题能反复跑、自动判分。
    • 真实会话：来自 iCode 的真实用户，含多轮交互与用户的纠正。题面和验收要求直接取自用户原话，判分对的是用户真正在意的东西。

    其他人通常只占其中一部分：有用户轨迹的拿不到代码仓和环境，有代码仓的没有真实用户的轨迹。

    出处：各家官方博客与公告；REAP arXiv 2604.01527；SWE-Bench Pro arXiv 2509.16941；GITS-Eval arXiv 2501.07531。

  2. 三条路径融合，从 coding 问题本身出发。业界公开的演进实践基本是单个 agent 的视角：沿着这个 agent 的组件由外到内改（第五节的六个层级，全是 agent 组件）。我们把一次 coding 失败拆成「没用上（Agent 组件）/ 不会（软件工程能力）/ 不知道（知识）」三类，分流到三条路径，再在同一批题上验证组合（短期这一类问题上的分工见第一节图 1）。

    收益不能直接相加——叠在已进化 harness 上的补丁可以 −15.7（HarnessBank，arXiv 2607.13683，2026-07）——所以融合本身需要分流与判据，是能力而不是堆叠。下面三条前期工作，正好各自对应一条路径。

  3. 路径 A · 自演进方向的前期工作：从零走通一条闭环。闭环的每一环都有团队自己的工作，串起来就是从环境、造题到归因、优化、训练的完整链路：

    • 造题与环境：Change2Task（arXiv 2607.28591，2026-07，ICLR 2027 投稿中）把历史改动反向注入当前健康版本造题，构造成功率 79.6%（900/1,130），环境时长 −58.4%、存储 −71.2%；正好解决「绿基线在主分支、会话在旧提交」这个部署难点（第三节）。
    • 归因：DoVer（arXiv 2512.06749，ICLR 2026），干预式故障定位。
    • 优化：AutoSaddler（arXiv 2608.23041，2026-08，预印本），harness 自动优化，即路径 A 本身。
    • 训练：Agent Lightning（arXiv 2608.17528），agentic RL 框架，对应模型侧的大闭环。

    RepoLaunch、SWE-bench-Live 作为参考工作。408b8c 的 v1→v7（第一节）就是这条链路在一道题上的实跑。

  4. 路径 B · 软件工程方向的前期工作。路径 B 要的代码定位、代码分析、测试生成、判分，正是团队软件工程方向的积累，覆盖需求、测试生成、判分、轨迹诊断、代码演化与复用、代码可靠性几个方向。代表作：

    • 代码演化：Evolution-aware Constraint Derivation for Software Remodularization（面向重新模块化的演化感知约束推导，TOSEM 2024）——变更影响分析与依赖约束，短期这一类问题直接用得上。
    • 测试生成：Beyond Coverage（超越覆盖率：用大模型增强测试套件的有效性，OOPSLA 2026）——逐条路径确认改到位。
    • 需求：A Unified Issue Resolution Benchmark for Requirement Clarification, Planning, and Code Generation for Coding Agents（面向 coding agent 的需求澄清、规划与代码生成统一基准，arXiv 2608.09072）。
    • 判分：Can LLMs Replace Human Evaluators?（大模型能取代人类评审吗？ISSTA 2025）。
    • 轨迹诊断：What Resolve Rate Hides（解决率掩盖了什么：coding agent 的轨迹结构诊断，arXiv 2607.06184）。

  5. 路径 C · 知识工程方向的前期工作。团队在知识工程上主要做过三件事，正好是短期这一类问题需要的三种知识来源：代码图谱（代码实体与依赖关系，补上状态读写边就能直接推传播面）、代码开发范式挖掘（从提交历史里挖「改这里通常也要改那里」的共变规律）、基于文档 / 文本知识图谱的 RAG（把文档里的契约与约定结构化后检索）。

    在此之上，我们对知识工程做了六份深读调研，收敛出几条约束：写入要增量追加、由确定性代码合并——整份重写会让知识库一步之内塌掉（ACE 实测从 18,282 token / 66.7 分跌到 122 token / 57.1 分；ACE: Agentic Context Engineering，arXiv 2510.04618，ICLR 2026）；每条知识必须自带适用边界与触发条件；知识是模型与病理特化的，跨场景迁移是真正的瓶颈。

  6. 演进机制本身也会变好：双循环。一阶每轮改 agent 的做法；二阶每隔若干轮复盘一阶，改进它「怎么提改动、怎么判改动有没有用」；后续再用二阶的纠偏信号训练过程评判模型（第十二节）。改进演进循环本身在学术界已有工作，共同的结论是必须固定一个 agent 改不动的锚；我们的锚是测试、同起点对照与人工抽检，都来自真实仓库。

    状态：一阶在 408b8c 上走通；二阶目前由人工复盘完成；训练过程评判模型是后续工作。

  7. 可信判据。造出的每道题都要过 D1–D9 门禁；判分由看不到参考 patch 的 verify agent 按检查点现场写测试（第九节）；产品仓上还能用行级采纳（用户最终留下了 agent 写的哪几行）反过来检验任务集是否可信。

  8. 不止看「能不能跑」。现有 RSI 工作大都只看功能正确；代码写完之后还要人长期维护，我们把可维护性、可读性等非功能维度从用户的话里提出来，纳入评测（第十三节）。

  9. 部署位置。跟着 iCode 服务端，轨迹天然可得、用户无感；每接入一个仓，题与判据就多一份，且越用越准（见第三节）。

✅ 另外几个前提
  • 时机对：模型能力刚刚够用，工业界刚开始规模应用
  • 问题真：填补工业界的三大缺口，解决真实痛点
  • 方法实：不依赖公开基准，从真实轨迹提取任务
  • 团队全：三方协同，职责清晰，生态健康

五、从哪里来：RSI 的现状与机会窗口

RSI（Recursive Self-Improvement，递归自我改进）指 AI 系统修改自己的代码、配置或策略，且改动持久化、影响后续版本，形成复合增长的改进循环。单轮内的自我修正、人工决定每一步的优化都不算。

学术界：设计空间已经铺开，规模没跟上

从单层优化（2024：DSPy、OPRO 改提示词）走到 harness 整体优化（2026），技能库、记忆、拓扑、权重都有人做。但实验规模停在数百题；泛化大幅缩水（同分布 +14，分布外只剩 +5）；没有生产可用的安全防御，也没有成本核算。

工业界：各家都在演进，没有一家全自动合并

我们按六个层级（下表）调研了 16 家公司的公开实践。三条模式多源交叉后仍成立：先把线上修正与用户反馈整理成评测题，再让 agent 提候选改动；离线评测与线上 A/B 必须同时过关；候选可以自动生成、开草稿，但发布仍保留人工门槛。

为什么是 coding agent，为什么是现在

代码能执行、能测试，对错可以客观判定，是 RSI 最好的试验场。模型能力刚刚够用（太弱则优化无效，太强则无改进空间），agent 框架已经稳定，工业界有了海量真实轨迹。缺的是基础设施：从轨迹到任务的方法、可靠的判据、多维度的优化框架——这正是下一节的三个缺口。

六、要补的三大缺口

工业界落地 RSI，卡住的不是算法不够优雅，而是缺少可落地的基础设施：

缺口现状我们怎么补
1 · 真实的环境与任务公开基准规模小（SWE-bench Verified 500 题），且被训练数据污染、判别力随时间衰减；工业界缺少从用户轨迹到可复现任务的系统方法从真实会话自动造题：每道题由环境、题面、验收三部分组成，回到会话起点重建现场
2 · 可靠的判据人工写测试成本高；测试绑定固定实现，接口对不上就判错；agent 学会「过测试」而不是解决问题验收检查点取自用户原话；看不到参考答案的 verify agent 按被测代码的接口现场写测试；判官单独校准
3 · 有效的优化维度学术界方法覆盖全但规模停在数百题；工业界有规模，缺「改了什么 → 怎么验证 → 凭什么留」的完整循环失败分流到三条路径，配对重跑验证，两级门决定保留还是回滚

十一、进化三层：用户侧、Agent侧、模型侧

三层是落地位置，回答「改动对谁生效」；三条路径（见第十二节）回答「改的是什么」。这是两个独立的维度，每条路径的改动都按适用范围决定落在哪一层：

  • 路径 A（Agent 组件）改的是有了 agent 才有的组件：用户提示词、系统提示词、skill、工具、harness、记忆。同一类组件既可以只对一个仓或一个团队生效（用户侧，如仓库说明文件、项目级 skill），也可以进 agent 主线、对所有用户生效（Agent 侧，如系统提示词、内置工具）。
  • 路径 B（软件工程能力）改的是需求工程、代码定位、测试生成、变更影响分析这类能力。它们在 agent 出现之前就有人在用、在研究，独立于 agent 体系；现在用 agent 来实现它们，或者用它们辅助提升 agent。通用的能力进 Agent 侧，只对某个仓成立的（如某个仓的测试约定）留在用户侧。
  • 路径 C（知识工程）同理：每条知识按自带的适用边界，决定留在用户侧还是进 Agent 侧。
  • 模型侧进化是独立的（agentic RL、特定能力微调），框架可提，2627 不做；第十二节双循环里后续要训的是过程评判模型，不是基模型。
层次对谁生效怎么演进
用户侧只对一个仓或一个团队，不出域从该用户的轨迹抽取成功模式，标注适用边界，匹配时才加载
Agent 侧所有用户，进 agent 主线，版本化可回滚从多个用户的轨迹提炼共性问题，留出集验证泛化，配对重跑与回归确认无负面影响
模型侧所有使用该模型的 agent同一批任务与轨迹做奖励信号训练权重；框架可提，2627 不做

十二、三条演进路径与双循环

三条路径按「改的是什么」划分。A 改 agent 自己的组件：提示词、skill、工具、harness、记忆，离开 agent 这些概念就不存在。B 改软件工程能力：需求工程、代码定位、测试生成等，它们早于 agent，独立于 agent 体系，agent 是实现它们的一种方式，也是它们服务的对象。C 改 agent 可用的知识。

三条路径并行推进，因为它们的做法与失效方式完全不同；后期在同一批任务上验证是否真的互补——收益不能直接相加。

演进闭环的双循环架构

三条路径回答「改什么」；双循环回答另一个问题：谁来提改动、谁来判它有没有用，以及这两件事本身怎么变好。一阶每轮改进 Executor（被进化的 agent）的做法；二阶每 n 轮复盘一阶，改进一阶提议与验证改动的方式。

原架构图的 strategy 在本文译为「做法」，指三条路径产出的 skill、工具、提示词、知识条目等可改部件。

多久一次改什么保留 / 回滚的依据在 408b8c 上对应什么
一阶每轮Executor 的做法：skill、工具、提示词、知识条目同起点配对重跑，Verifier 判断上次修改是否有效v1→v7 每一版：提改动 → 配对重跑 → 保留或回滚。v1–v2 没被加载，v3 能触发但不稳定，v6 起 1.0×3
二阶每 n 轮一阶的 Reflector 与 Verifier：怎么提议、怎么验证改后一阶 n 轮是否比改前好由人工复盘完成。S5 把这题的定性从「题面不完整」订正为「agent 的真实能力缺口」（改的是一阶的诊断）；v6→v7 发现触发贴着题面措辞，把提议方式从「按题面写触发」改成「按 DRY 原则写判据」（改的是一阶的提议）
后续 RSI²—一阶、二阶各训练一个过程评判模型一阶看 Evaluator + 二阶纠偏信号；二阶看改后 n 轮是否变好未开始

这套双循环的锚是测试、同起点对照与人工抽检：一阶的判断由二阶复盘来审，二阶给出的修改方向写进训练之前，先从同一起点重跑确认确实更好。训练对象是过程评判模型，Executor 底下的基模型不动。

十三、超越功能正确性：非功能需求维度

现有 RSI 工作大都强调任务完成的成功率/准确性（功能正确）， 而忽略了软件的非功能需求。我们的代码写出来之后，比较长一段时间内还是需要人负责的。 所以软件的非功能需求非常重要。这是我们与现有工作的重要差异点。

维度 定义 如何从轨迹中提取 如何检查
可靠性 稳定性、容错、边界处理 用户提及"经常崩溃"、"边界情况没处理" 异常处理覆盖、边界检查
可用性 易用、符合习惯、接口设计 用户提及"不好用"、"接口不直观" 接口设计规范、参数合理性
可维护性 易改、易扩展、模块化 用户提及"改起来太麻烦"、"逻辑太复杂" 圈复杂度、重复代码、模块耦合度
可读性 易懂、有注释、命名清晰 用户提及"看不懂"、"缺少注释" 命名规范、注释完整性、代码风格
性能 时间效率、空间效率 用户提及"太慢了"、"内存占用太高" 时间复杂度、内存占用、热点分析
安全性 输入验证、权限检查、敏感信息保护 用户提及"安全问题"、"权限没检查" 静态分析（SQL 注入、XSS）、权限检查

做法是从用户的对话与修改行为里提取这些关注点，做相应检查（如圈复杂度、重复代码、命名与注释、异常与边界处理），并提取专门针对非功能需求的任务，用于评测与演进。

十四、未来图景：3 年后的 Coding Agent

如果做成了，2028 年的 coding agent 在用户自己的仓上越用越好，不再重复犯纠正过的错误，写出的代码不仅能跑而且好维护；新模型发布后一周内完成适配验证；skill 库失效的自动下线、有效的自动推广。
